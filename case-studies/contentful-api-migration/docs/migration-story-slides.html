2 · How AI did it

The full plan — 15 tasks, executed one branch at a time

The plan — executed top to bottom

  1. Foundation & generic core
  2. DTO contract & conventions
  3. Page endpoints + slugs
  4. Sections (polymorphic)
  5. Blog
  6. HelpCenter & articles
  7. Glossary
  8. Parity / validation harness
  9. Content gateway: cache & resilience
  10. Slug allow-list & webhook
  11. Observability
  12. Benchmarks & reports
  13. Payload optimization
  14. CORS & preview origin
  15. Hosting & cutover

Executed sequentially

One task at a time in dependency order. Tasks that touch the same files never ran at once — no merge conflicts, no half-finished state — and each finished green (clean build + tests) before the next began.

One branch & PR per task

Every task checked in on its own branch (feat/task-03-page). Git history maps 1:1 to the plan — fully traceable, and any task can be reviewed, reverted or fixed in isolation.

Each task carried its own context file — objective, dependencies, source-of-truth legacy references, deliverables and acceptance criteria — so AI built exactly what was scoped and self-checked against an objective gate.

4 · The human in the loop

AI moved fast — the author gave it direction

What the human brought — experience & context

  • Concrete API contracts: every endpoint & response stays identical (new fields are additive-safe; nothing changed or removed) → zero consumer impact and a true drop-in cutover.
  • Parity testing: all endpoints and responses verified against recorded fixtures — removing the QA dependency and catching every edge case automatically → parity from stuck to 36 / 36.
  • Domain instinct: “don't accept ‘it can't be done’ — verify against the live API.” → the date, ordering & search “limitations” proved to be code bugs, and were fixed.

Where AI fell short

  • Mistook parity gaps for “platform limitations” — and stopped instead of digging deeper.
  • Treated every tiny response difference as a hard blocker; progress plateaued.
  • Would have crippled the redesign to mirror quirks of the old output — lacking the judgment to know which differences actually mattered.

AI will close this gap very soon.

Under load the redesign clears the run in 8.3 s vs 52.9 s (mean 676 ms vs 5,035 ms). Invalid slugs are short-circuited by the redesign's slug allow-list — a 404 returns in ~8 ms with no upstream fetch, protecting the backend from bad/abusive traffic; the existing API still reaches out (~70 ms).
