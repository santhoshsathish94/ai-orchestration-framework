CMS API — REST Rewrite

Architecture overview in plain terms · same API, simpler engine, safer & faster

What we're doing (in one paragraph)

The CMS API takes content from Contentful and serves it to our websites as JSON. Today it talks to Contentful using GraphQL, which needs a lot of hand-written code. We're rebuilding it to use Contentful's REST API with one small, generic converter. The public API does not change — same URLs, same JSON — so nothing that consumes it has to change. Along the way we make it lighter, faster, harder to abuse, and easier to watch.

Before & after

Today — GraphQL

  • ~30 GraphQL query files + fragments
  • A builder that fetches a page twice (discover, then fetch)
  • ~200 hand-written model classes + a ~900-line mapping profile
  • A second network call just to resolve links inside rich text
  • Cache used as a normal 1-day cache (can serve stale content)

New — REST

  • One REST call with include=10 returns the page and everything it links to
  • One generic converter turns any content type into our DTOs
  • No GraphQL files, no model zoo, no AutoMapper
  • Rich-text links come back in the same call — no extra round trip
  • Cache is a safety net, not a staleness layer (details below)

Three projects: Contracts (the API shape), Contentful (the engine), Api (the host). That's the whole thing.

The one clever idea: a generic converter

Instead of a class per content type, we describe each field on the DTO with a small attribute, and one converter reads those rules for any content type.

Read the field

Default: match the Contentful field name; override with [ContentfulField].

Follow links

Linked entries/assets are stitched in from the same response; lists become [Collection].

Render rich text

[RichText] turns Contentful rich text into the same HTML the old API produced.

Because the DTOs are copied over unchanged, the exact JSON shape — including the polymorphic kind labels on sections — stays identical.

Caching = safety net, not staleness

Normal times

Every request goes live to Contentful (it's fast and CDN-backed). We quietly save a copy in the background.

If Contentful has a problem

We instantly serve the last saved copy, so the site stays up. A circuit breaker avoids waiting on timeouts; duplicate simultaneous requests are collapsed into one.

Preview/draft requests are always live (never cached).

Protecting against abuse (recent DoS)

The problem

An attacker hammered random slugs. Each unknown slug used to become an upstream call — amplifying the attack.

The fix

We keep an allow-list of real slugs. Unknown slug → instant 404, no upstream call. A secured Contentful webhook keeps the list current when content is published/unpublished. (Rate limiting stays at the gateway/CDN.)

Knowing when something's wrong

Full OpenTelemetry (traces, metrics, logs) into App Insights. Dashboards show the signals that matter:

Plain-English glossary

DTO

The exact shape of the JSON we return. It is the contract.

Includes

Contentful returns linked items alongside the main one so we can stitch them together.

Circuit breaker

If Contentful keeps failing, we stop calling it for a bit and serve cache instead.

Preview

Draft content for editors; always fetched live, never cached.
